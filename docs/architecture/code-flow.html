agentsys — Harness Code Execution Flow

How a request becomes a validated, capability-scoped agent runtime. This walks the real code that exists today (src/agentsys/harness/): the loader, the tool registry, and the capability injector. The model is the brain; this is the OS that decides what it is allowed to be and do.

The three modules

loader.py

Turns markdown definition folders into one validated, immutable AgentDefinition.

  • resolve() — entry point
  • load_generic() / load_override()
  • merge() — directives + invariants
  • AgentDefinition (frozen)

registry.py

The code-side authority on which tools exist. Markdown only references names.

  • ToolSpec — name, required_permissions, connector
  • ToolRegistry — register / get / names
  • ToolNotFoundError

injector.py

Computes the enforced tool surface for one agent + identity (Layer 1).

  • resolve_tool_surface()
  • effective = role ∩ granted
  • InjectionResult — granted / denied

Execution flow — click a step to expand

Scenario: instantiate the sales-agent role for client badie, for a user whose RBAC grants a set of permissions.

1
resolve(role_type="sales-agent", client="badie", roots)
Public entry point. Orchestrates load → merge → return. Where any agent instantiation begins.

What it does

Loads the generic role, loads the client override if it exists, merges them, and returns a frozen AgentDefinition. If no override exists for that client, the generic definition is returned unchanged — clients onboard gradually. 
def resolve(role_type, *, client=None, roots=None) -> AgentDefinition:
    generic = load_generic(role_type, roots=roots)
    if client is not None:
        override = load_override(client, role_type, roots=roots)
        if override is not None:
            return merge(generic, override)   # validated here
    return _wrap(generic)               # no override → generic as-is
2
load_generic("sales-agent") → RawDefinition
Reads platform/roles/sales-agent/{role,manifest,policy}.md and parses the YAML frontmatter.

What it does

Reads the three files of the generic role folder. _split_frontmatter() separates the YAML block (machine-readable config) from the markdown body. The body of role.md becomes the system_prompt verbatim — that is the only "prose for the model". Everything else is structured config. 
# platform/roles/sales-agent/
role.md     → frontmatter {name, version}  +  BODY = system_prompt
manifest.md → tools, skills, context, permissions
policy.md   → autonomy, escalation_rules, delegation_policy,
              memory_policy, audit_policy, execution_limits
Key idea: the markdown provides context (the prose). The structured fields are parsed only from YAML frontmatter — the loader never interprets prose.
3
load_override("badie", "sales-agent") → RawDefinition | None
Reads deployments/badie/sales-agent/… — the client's specialization. Returns None if the folder doesn't exist.

What it does

Same parsing as step 2, but for the deployment folder. The override carries client-specific tools/skills and merge directives (e.g. permissions: inherit, escalation_rules: {inherit: true, add: [...]}). It also carries the BADIE role.md body (Argentine Spanish, vocabulary) which becomes the system prompt.
4
merge(generic, override) → AgentDefinition
The deterministic core. Validates invariants, applies merge directives, returns the frozen result. Raises DefinitionError on any violation.

Validation runs FIRST — fail loud

InvariantRule
autonomyoverride rank ≤ parent rank  (confirm 0 < supervised 1 < full 2)
toolsset(override.tools) ⊆ set(parent.tools)
permissionsresolved permissions ⊆ parent permissions
execution_limitseach override limit ≤ parent / platform default
The invariant that matters: a deployment can only restrict or specialize — never elevate. This is architecture enforced as code: an override that tries to grab a tool or permission the generic role doesn't have makes merge() raise, and the runtime is never built.

Then merge directives are applied

DirectiveResult
field absentinherit parent value unchanged
inherittake parent value as-is
{inherit: true, add: [...]}parent list + additions
{inherit: true, remove: [...]}parent list − removals
{override: value}replace entirely (still validated)
5
ToolRegistry.register(ToolSpec(...)) · built at startup
The platform registers every real tool once. A manifest can only name tools that live here. Unknown name → it does not exist.

What it does

The registry is the single source of truth for what tools the platform provides. Each ToolSpec couples a name to the permissions it requires and the executable connector. 
@dataclass(frozen=True)
class ToolSpec:
    name: str
    required_permissions: tuple[str, ...]
    connector: Callable[..., Any]   # the executable

registry.get("unknown_tool")   # → raises ToolNotFoundError
6
resolve_tool_surface(definition, registry, granted_permissions) → InjectionResult
Layer 1 enforcement. Computes which tools this agent + this identity may actually use.

The resolution — effective = role ∩ granted

def resolve_tool_surface(definition, registry, granted_permissions):
    effective = set(definition.permissions) & set(granted_permissions)
    granted, denied = [], []
    for name in definition.tools:
        if name not in registry:
            raise InjectionError(name)        # fail loud
        spec = registry.get(name)
        if set(spec.required_permissions) <= effective:
            granted.append(spec)
        else:
            denied.append((name, "missing permissions: …"))
    return InjectionResult(granted, denied)
Why the intersection: a tool is usable only if the role allows the permission AND the user was granted it. The role caps it; the user identity caps it again. Neither alone is enough.

The data that flows through

AgentDefinition (frozen — the validated snapshot)

role_name · version · deployment · # identity
system_prompt                       # role.md body, verbatim
tools · skills · context · permissions    # from manifest.md
autonomy · escalation_rules · delegation_policy
memory_policy · audit_policy · execution_limits   # from policy.md

InjectionResult (the enforced surface)

granted: tuple[ToolSpec, ...]            # what the agent may call
denied:  tuple[(tool_name, reason), ...] # filtered out, with why

What is NOT built yet

The flow above stops at the resolved surface. Still ahead (Wave 2+): the Agent Factory (assembles prompt + tools + skills + policy into a runtime), Layer 2 — the Tool Call Interceptor (runtime enforcement: block + audit + escalate), the Agent Runtime (LangGraph + bind_tools + the LLM), the System Router, and the audit/memory sinks. This page covers loader + registry + injector only — the deterministic foundation everything else builds on.
