agentsys — Guía del sistema

Qué es la plataforma, qué roles define, qué archivos la componen, y cómo se ejecuta el harness paso a paso. El modelo es el cerebro; el harness es el sistema operativo que decide qué tiene permitido ser y hacer. Pensado para entender el sistema antes de avanzar.

¿Qué es la plataforma?

agentsys es una plataforma de agentes reutilizable, no un bot. El bot de WhatsApp de BADIE es solo el primer deployment que corre sobre ella. La plataforma es el producto; cada cliente es una implementación. Esa separación es la regla que organiza todo el repo.

Core Platform

El runtime genérico, agnóstico al cliente. IP de la plataforma.

  • roles genéricos en platform/roles/
  • el harness (loader, registry, injector)
  • RBAC, lifecycle, auditoría

Deployment (cliente)

La especialización concreta. Ej: BADIE.

  • overrides en deployments/badie/
  • skills propias del dominio
  • solo puede restringir o especializar, nunca elevar

Los cuatro módulos

loader.py

Convierte las carpetas de definición en markdown en un único AgentDefinition validado e inmutable.

  • resolve() — punto de entrada
  • load_generic() / load_override()
  • merge() — directivas + invariantes
  • AgentDefinition (congelado)

registry.py

La autoridad, del lado del código, sobre qué tools existen. El markdown solo referencia nombres.

  • ToolSpec — name, required_permissions, connector
  • ToolRegistry — register / get / names
  • ToolNotFoundError

injector.py

Calcula la superficie de tools que se hace cumplir para un agente + identidad (Capa 1).

  • resolve_tool_surface()
  • effective = rol ∩ otorgados
  • InjectionResult — granted / denied

factory.py

El ensamblador. Llama al loader y al injector, recibe el registry y se lo pasa al injector, y agrega la carga de skills + la composición del prompt. No decide seguridad: solo pega y compone.

  • build_runtime() — punto de entrada
  • compone el system_prompt (role + skills)
  • carga skills/*.md del deployment
  • EquippedRuntime — definition · prompt · tools · skills

Flujo de ejecución — hacé clic en un paso para expandir

Escenario: instanciar el rol sales-agent para el cliente badie, para un usuario cuyo RBAC le otorga un conjunto de permisos.

1
resolve(role_type="sales-agent", client="badie", roots)
Punto de entrada público. Orquesta cargar → fusionar → devolver. Donde arranca toda instanciación de agente.

Qué hace

Carga el rol genérico, carga el override del cliente si existe, los fusiona y devuelve un AgentDefinition congelado. Si no existe override para ese cliente, devuelve el genérico sin cambios — los clientes se incorporan de a poco. 
def resolve(role_type, *, client=None, roots=None) -> AgentDefinition:
    generic = load_generic(role_type, roots=roots)
    if client is not None:
        override = load_override(client, role_type, roots=roots)
        if override is not None:
            return merge(generic, override)   # acá se valida
    return _wrap(generic)               # sin override → genérico tal cual
2
load_generic("sales-agent") → RawDefinition
Lee platform/roles/sales-agent/{role,manifest,policy}.md y parsea el frontmatter YAML.

Qué hace

Lee los tres archivos de la carpeta del rol genérico. _split_frontmatter() separa el bloque YAML (config máquina-legible) del cuerpo markdown. El cuerpo de role.md se vuelve el system_prompt textual — esa es la única "prosa para el modelo". Todo lo demás es config estructurada. 
# platform/roles/sales-agent/
role.md     → frontmatter {name, version}  +  CUERPO = system_prompt
manifest.md → tools, skills, context, permissions
policy.md   → autonomy, escalation_rules, delegation_policy,
              memory_policy, audit_policy, execution_limits
Idea clave: el markdown aporta contexto (la prosa). Los campos estructurados se parsean solo desde el frontmatter YAML — el loader nunca interpreta prosa.
3
load_override("badie", "sales-agent") → RawDefinition | None
Lee deployments/badie/sales-agent/… — la especialización del cliente. Devuelve None si la carpeta no existe.

Qué hace

El mismo parseo que el paso 2, pero sobre la carpeta del deployment. El override trae tools/skills específicos del cliente y directivas de merge (por ej. permissions: inherit, escalation_rules: {inherit: true, add: [...]}). También trae el cuerpo del role.md de BADIE (español rioplatense, vocabulario) que se vuelve el system prompt.
4
merge(generic, override) → AgentDefinition
El núcleo determinístico. Valida invariantes, aplica las directivas de merge y devuelve el resultado congelado. Lanza DefinitionError ante cualquier violación.

La validación corre PRIMERO — falla fuerte

InvarianteRegla
autonomyrango del override ≤ rango del padre  (confirm 0 < supervised 1 < full 2)
toolsset(override.tools) ⊆ set(parent.tools)
permissionspermisos resueltos ⊆ permisos del padre
execution_limitscada límite del override ≤ padre / default de plataforma
El invariante que importa: un deployment solo puede restringir o especializar — nunca elevar. Esto es arquitectura hecha cumplir como código: un override que intente agarrar un tool o permiso que el rol genérico no tiene hace que merge() lance, y el runtime nunca se construye.

Después se aplican las directivas de merge

DirectivaResultado
campo ausentehereda el valor del padre sin cambios
inherittoma el valor del padre tal cual
{inherit: true, add: [...]}lista del padre + agregados
{inherit: true, remove: [...]}lista del padre − quitados
{override: value}reemplaza por completo (igual se valida)
5
ToolRegistry.register(ToolSpec(...)) · se arma al iniciar
La plataforma registra cada tool real una vez. Un manifest solo puede nombrar tools que viven acá. Nombre desconocido → no existe.

Qué hace

El registro es la única fuente de verdad sobre qué tools provee la plataforma. Cada ToolSpec acopla un nombre a los permisos que requiere y al connector ejecutable. 
@dataclass(frozen=True)
class ToolSpec:
    name: str
    required_permissions: tuple[str, ...]
    connector: Callable[..., Any]   # el ejecutable

registry.get("unknown_tool")   # → lanza ToolNotFoundError
6
resolve_tool_surface(definition, registry, granted_permissions) → InjectionResult
Enforcement de Capa 1. Calcula qué tools puede usar realmente este agente + esta identidad.

La resolución — effective = rol ∩ otorgados

def resolve_tool_surface(definition, registry, granted_permissions):
    effective = set(definition.permissions) & set(granted_permissions)
    granted, denied = [], []
    for name in definition.tools:
        if name not in registry:
            raise InjectionError(name)        # falla fuerte
        spec = registry.get(name)
        if set(spec.required_permissions) <= effective:
            granted.append(spec)
        else:
            denied.append((name, "faltan permisos: …"))
    return InjectionResult(granted, denied)
Por qué la intersección: un tool es usable solo si el rol permite el permiso Y el usuario lo tiene otorgado. El rol lo limita; la identidad del usuario lo limita de nuevo. Ninguno por sí solo alcanza.
7
build_runtime(role_type, registry, granted_permissions, *, client, roots) → EquippedRuntime
El ensamblador (src/agentsys/harness/factory.py). Orquesta los pasos 1–6, carga las skills y compone el system prompt → un runtime equipado listo para el motor.

Cómo orquesta — pega todo lo anterior, sin lógica de seguridad nueva

El factory no decide permisos ni valida invariantes (de eso ya se encargaron el loader y el injector). Llama a los módulos en orden, suma las skills del deployment y compone el prompt final. 
def build_runtime(role_type, registry, granted_permissions, *, client=None, roots=None):
    definition = resolve(role_type, client=client, roots=roots)        # pasos 1–4
    surface    = resolve_tool_surface(definition, registry, granted_permissions)  # paso 6
    skills     = _load_skills(definition, client, roots)              # lee deployments/.../skills/*.md
    system_prompt = _compose_prompt(definition, skills)             # role body + skills
    return EquippedRuntime(definition, system_prompt,
                           surface.granted, surface.denied, skills)

Su relación con cada módulo — orquesta 2, recibe 1, agrega 2

MóduloCómo lo usa el factory
loaderLo llama — resolve() → AgentDefinition
injectorLo llama — resolve_tool_surface() → tools concedidas / denegadas
registryNO lo llama. Lo recibe como parámetro y se lo pasa al injector — el injector es quien lo lee. El registry se arma una vez al iniciar (con los connectors reales); el factory no sabe cómo se construye. Por eso es testeable: en los tests recibe un registry de prueba con callables falsos.
skills/*.mdTrabajo propio — los lee de deployments/{client}/{role}/skills/. El loader nunca toca estos archivos.
composiciónTrabajo propio — arma el system_prompt (role body + skills).
La regla que lo gobierna: el factory no decide nada de seguridad. No valida invariantes (eso es del loader) ni resuelve permisos (eso es del injector). Solo pega y compone. El verify independiente confirmó que no introduce ni una sola decisión de seguridad nueva — por eso es simple y predecible.

Cómo se arma el system_prompt

Regla de composiciónDetalle
ordencuerpo de role.md primero, después cada skill en el orden del manifest
contenidoel archivo de cada skill se concatena textual — el factory no reescribe títulos ni reformatea (pasa el contenido, respeta al autor)
separadorlos bloques se unen con \n\n---\n\n
rol genérico (sin cliente)no tiene skills → el prompt es solo el cuerpo del role.md
skill declarada sin archivoFactoryError — falla fuerte, igual que el loader y el injector
Por qué textual y no generado: las skills ya se auto-titulan (# Skill: order_extraction). Si el factory regenerara el texto, perdería la intención del autor. Mismo principio que el resolver de skills: se pasa el contenido, no un resumen. El resultado es determinístico — mismos archivos, mismo prompt, byte a byte.

Los datos que fluyen

AgentDefinition (congelado — la instantánea validada)

role_name · version · deployment · # identidad
system_prompt                       # cuerpo de role.md, textual
tools · skills · context · permissions    # de manifest.md
autonomy · escalation_rules · delegation_policy
memory_policy · audit_policy · execution_limits   # de policy.md

InjectionResult (la superficie que se hace cumplir)

granted: tuple[ToolSpec, ...]            # lo que el agente puede llamar
denied:  tuple[(tool_name, reason), ...] # filtrados, con el motivo

EquippedRuntime (el runtime equipado — lo que arma el factory)

definition:   AgentDefinition           # referencia: context/policy/autonomy viven acá
system_prompt: str                       # compuesto: role body + skills
tools:        tuple[ToolSpec, ...]       # las concedidas (de InjectionResult)
denied_tools: tuple[(name, reason), ...] # las filtradas, para auditoría
skills:       tuple[LoadedSkill, ...]    # name + content, leídas de disco

Lo que TODAVÍA no está construido

El flujo de arriba termina en el runtime equipado (EquippedRuntime), pero ese objeto todavía es inerte: nadie lo ejecuta aún. Falta (Wave 2+): el Agent Runtime (LangGraph + bind_tools + el LLM — el motor que pone vivo al runtime), la Capa 2 — el Tool Call Interceptor (enforcement en runtime: aplica los execution_limits, bloquea + audita + escala), los connectors reales (hoy son callables de prueba: message_sender vía Meta Cloud API, catalog_search vía pgvector, etc.), el System Router y los sumideros de auditoría/memoria. Esta página cubre loader + registry + injector + factory — el cimiento determinístico sobre el que se construye todo lo demás.
