Layer 1 — Build-time
Capability Injector · runs once when the runtime is assembled
1
Loader reads role.md + manifest.md + policy.md from the agent definition folder → produces AgentDefinition with tools[] and permissions[].
2
Injector computes effective permissions:
effective = role.permissions ∩ granted_permissions
This is the intersection of what the role declares and what the calling identity actually holds.
3
For each tool name in manifest.tools:
— Not in registry → InjectionError (fail loud, deterministic)
— spec.required_permissions ⊆ effective → granted
— Otherwise → denied (with reason naming missing perms)
4
Factory composes system prompt and assembles a frozen EquippedRuntime. Only granted tools are in runtime.tools. These are passed to the LLM via bind_tools() — the model cannot see or call anything outside this list.
Layer 2 — Call-time
Tool Call Interceptor · runs on every tool invocation during the LLM loop
1
Model generates a tool call. Before the connector fires, intercept() receives tool_name, tool_input, and the EquippedRuntime.
2
Surface check: build a lookup dict {t.name: t for t in runtime.tools}. If tool_name not in surface → log interceptor.call_blocked (reason: not_in_surface) → raise PolicyViolation.
3
Sensitivity check: a tool is sensitive if any required_permission starts with write: or send:. Sensitive tools require current_permissions at call time.
4
If sensitive and no current_permissions → block (revalidation_required).
If sensitive and spec.required_permissions ⊄ current_permissions → block (permission_revoked).
5
All checks pass → log interceptor.call_allowed → execute spec.connector(tool_input) → log interceptor.call_executed → return CallResult.

Why both layers are mandatory
What Layer 1 prevents
  • Model calling tools it was never told about
  • Tools being used before permission is verified
  • Unregistered tool names reaching the LLM
What Layer 2 catches that L1 can't
  • Model hallucinations of valid-looking tool names
  • Prompt injection that forges a tool call
  • Bugs in the injection pipeline (incomplete surface)
  • Permission changes after runtime was built

EquippedRuntime — the central data object

Frozen dataclass produced by the factory. Everything downstream reads from it — the Agent Runtime, the interceptor, the audit trail.

definition
AgentDefinition
The resolved agent spec: role name, tools list, permissions, skills, autonomy level, execution limits, policies.
system_prompt
str
Composed prompt: role body + each skill file body, joined by --- in manifest declaration order.
tools
tuple[ToolSpec, ...]
Granted tool surface. Only tools that passed the L1 RBAC check. Passed to the LLM via bind_tools().
denied_tools
tuple[tuple[str, str], ...]
Tools that were declared but denied, with their reason. Used for audit and debugging.
skills
tuple[LoadedSkill, ...]
Deployment skill files loaded from disk. Each has a name and the full markdown content.

The missing link — stub → real connector (the async friction)

Today — the stub
catalog_search(dict) → dict
sync · hardcoded 5 products
Target — the real connector
await rag.search_catalog(
  session, query, embedder)
async · needs AsyncSession
The conflict: ToolSpec.connector is sync (dict→dict), and the runtime wraps it in asyncio.to_thread. But rag.search_catalog is async — it needs a SQLAlchemy AsyncSession. Drop an async connector into a sync slot and you get a coroutine that's never awaited. D-009 resolves this by teaching the interceptor + runtime to support async-native connectors.

⚠ The connector never commits. The transaction (commit/rollback) is closed by the orchestrator (webhook), not by the data-access function — pure persistence in, entity out.
Why this is surgical
D-009 changes one pivot — the connector dispatch inside intercept. Everything above it (instantiation, the LangGraph loop, L1 RBAC, L2 enforcement) stays identical. The only structural ripple: intercept() becomes async def (so the 7 interceptor tests become async), and EquippedRuntime gains an optional session_provider (default None, so every existing construction site keeps working). It earns the name "the heart" because it is the exact seam where the harness meets the real database.
