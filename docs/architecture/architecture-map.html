2 · Flujo de un turno (request lifecycle)

sequenceDiagram participant U as Cliente participant E as Entry (adapter / webhook) participant R as AgentRuntime participant L as LLM participant I as Interceptor (L2) participant C as Connector participant D as Data U->>E: mensaje E->>R: run_turn(messages, permissions) loop hasta AIMessage sin tool_calls R->>L: call_model(historial) L-->>R: respuesta (tool_calls?) alt hay tool_calls R->>I: intercept(tool, args, perms, session) I->>I: valida surface + revalida si sensible I->>C: connector(inputs, session) C->>D: query (RAG / SQL / stub) D-->>C: datos C-->>I: dict resultado I-->>R: ToolMessage end end R-->>E: mensajes del turno E-->>U: respuesta final

5 · Notas que el mapa deja a la vista

Gap (P1): el webhook está desconectado del runtime — hoy solo el adapter cablea de verdad.
Dónde entra lo nuevo: la capa de ejecución (sandbox + tools Python/SQL/shell) se enchufa como connectors nuevos detrás del interceptor. El patrón ya existe (catalog_search); la diferencia es que esos connectors correrán dentro del sandbox en vez de in-process. Ese es el corazón del próximo diseño.
