# Exploration: library-first-agents

## Current State

**Role resolution is folder-name lookup inside one fixed root, not a locator.**
- `_role_folder` (`src/agents_system/harness/loader.py:667-668`): `platform_root / "roles" / _validate_segment(role_type, kind="role_type")`. Hardcoded to `platform_root/roles`; there is no notion of "load this role from an arbitrary importer folder."
- `_load_role_files` (`loader.py:880-945`) calls `_role_folder` and reads `role.md`/`manifest.md`/`policy.md` from that fixed location only.
- `_extends_target` (`loader.py:836-843`): `str(raw).strip().rstrip("/").rsplit("/", 1)[-1]` — keeps only the LAST path segment. `extends: platform/roles/agent` and `extends: some/importer/path/agent` both collapse to bare `agent`, then `_resolve_role_chain` (`loader.py:1102-1149`) re-resolves that bare name via `_load_role_files` against `platform_root/roles` again. The path form is cosmetic today, not functional — `extends:` cannot leave `platform_root`, and cannot reference an importer-defined custom agent at all (own docstring on `_extends_target` already flags this: "Every manifest already on disk writes the path form... so that form has to keep meaning what it looks like it means").
- `load_generic` (`loader.py:1152-1178`) is unconditionally the FIRST call inside `resolve()` (`loader.py:1809-1882`, generic loaded at line 1831 before any override logic). There is no branch for "this role definition was supplied directly, not looked up by name."
- `load_override` (`loader.py:1218-1302`) reads `deployments/{client}/{role_type}/` and enforces (`loader.py:1264-1274`) that a deployment's `extends:` (if declared) must equal its own `role_type` — deployments cannot choose a different parent; this part is intentionally rigid and should stay that way for predefined-role overrides.
- `merge`/`_merge_validated`/`_validate_tools` (`loader.py:1630-1655`, `1423-1432`) enforce the **subtractive-only** deployment invariant: an override's `tools` must be a subset of the generic role's tools. This is the mechanism `docs/platform/deployment.md`'s "Permission invariant: A deployment can only restrict or specialize. It can never elevate" describes, and it is unaffected by anything below — it stays load-bearing for predefined-role deployment overrides.

**The generic/base agent already exists as `base -> agent`.**
- `platform/roles/base/{role,manifest,policy}.md`: abstract (`abstract: true`), no tools, one permission (`read:session`), `autonomy: supervised` floor, `delegation_policy.allowed: false`. `resolve("base")` raises by design (abstract roles refuse direct resolution).
- `platform/roles/agent/{role,manifest,policy}.md`: `extends: platform/roles/base`, adds `tools: [session_state, escalation_notifier]`, `permissions: [read:session, send:escalation]`. This IS the "generic agent" the change intent calls for — the ADR-002 D role tree confirms it: `base (abstract) -> agent -> {sales,data,support,summary,accountant,orchestrator,operator-agent -> developer-agent}`.
- The 8 packaged roles all extend `agent` (directly or via `operator-agent`). No code or doc currently calls `agent` "generic" as a *distinguishing* term from the 8 roles — "generic" is used loosely throughout for "platform-owned" (e.g. `docs/platform/deployment.md`'s "Generic roles define the behavioral template"). Renaming is a terminology change, not a structural one — the tree itself is already exactly what the change intent wants.

**Skills load only from `deployments/{client}/{role}/skills/`, never from a role's own folder.**
- `_load_skills` (`src/agents_system/harness/factory.py:97-166`): builds `skills_dir = deployments_root/{client}/{definition.role_name}/skills/`. Raises `FactoryError` if `client is None` and `definition.skills` is non-empty (`factory.py:106-112`) — i.e. a role with declared skills but no deployment context cannot resolve them at all today.
- `docs/platform/deployment.md:91-93`: "Skills are always client-specific. There are no generic skills. The `skills/` folder exists only in deployments." This directly contradicts `docs/platform/role.md:7` ("...plus an optional `skills/` subdirectory") — a pre-existing doc inconsistency that becomes load-bearing once an importer Agent folder is expected to carry its own skills.

**Runtime id and serving: `{deployment}__{role}` with a `_generic` sentinel, parsed independently in two places.**
- `integration/openai_adapter.py:52-72` (`to_model_id`/`parse_model_id`): `prefix = deployment if deployment is not None else "_generic"`; `f"{prefix}__{role}"` / inverse split on `"__"`.
- `main.py` lifespan (`main.py:280-370`, esp. `283-308`): independently re-implements the same split (`prefix, role = model_id.split("__", 1)`, `deployment = None if prefix == "_generic" else prefix`) rather than calling `parse_model_id` — two independent parsers of the same format, a drift risk of exactly the kind this repo's own ADR-002 F.19-21 items document elsewhere (stale duplicated conventions).
- `role` in every path is always resolved via `resolve(role, client=deployment, roots=roots)` (`main.py:304-308`), i.e. always a `platform_root/roles/<name>` folder name. **There is no path today for `create_app`/the adapters to serve an importer-defined custom agent** — only predefined (packaged) roles, optionally deployment-overridden.
- `granted_permissions=definition.permissions` (`main.py:357-364`, comment "AD-5", `main.py:299-301`): the deployer-facing "grant" step is currently a pass-through of the role's OWN full resolved permission set, always, automatically. This is worth flagging precisely for guard #2 below.

**`agents_system/__init__.py`** (`src/agents_system/__init__.py:60-73`): lazy `_EXPORTS` dict exposes `ToolRegistry`, `ToolSpec`, `Tier`, `ToolNotFoundError`, `RootConfig`, `AgentDefinition`, `resolve`, `DefinitionError`, `build_runtime`, `EquippedRuntime`, `FactoryError`, `InjectionError`, `AgentRuntime`. No `Agent`/`AgentSpec`/importer-facing constructor exists yet.

**`tests/platform_role_contract.py`** pins the packaged role set: `discover_platform_roles()` (lines ~35-48) walks `platform_root/roles` on disk; `discover_concrete_platform_roles()` filters `abstract: true`; `EXPECTED_ROLE_TOOLS` is a hand-written literal dict, independently graded against each resolved surface (deliberately NOT self-referential — "grading a resolved surface against `set(definition.tools)` grades the manifest against itself"). This is the existing "8 roles" pin the task description refers to.

**No SemVer/CHANGELOG enforcement exists anywhere.** `version` is a free-text frontmatter string (`role.md`/`manifest.md`, e.g. `version: "1.0"`), carried through `RawDefinition.version` → `AgentDefinition.version` with zero validation of format and zero diffing against any prior "released" state. No `CHANGELOG.md` file exists in the repo (`find` for `CHANGELOG*` returned nothing). Guard #1 (strict SemVer + CHANGELOG entry on any predefined-role tools/permissions change) is entirely greenfield.

**The injector already enforces real grant-intersection semantics — the gap is only at the caller.** `resolve_tool_surface`/`resolve_command_tool_surface` (`src/agents_system/harness/injector.py:102-169`, `172-224`) compute `effective = set(definition.permissions) & set(granted_permissions)` (line 107, line 187) and deny anything outside it via `_deny_reason` (lines 77-99, including the ADR-002 C.10 untrusted_input+T3 second barrier at 87-95). **This mechanism already does exactly what guard #2 asks for** — it is `main.py`'s lifespan that currently defeats it by always passing the role's full permission set as the grant (see above), not a missing capability in the injector.

**Universal library invariants already apply role-agnostically inside `resolve()`, which is encouraging for guard enforcement:**
- ADR-002 B.8/B.9 base prompt contract: `_append_base_contract` is called on every `resolve()` exit path — the override-merged branch (`loader.py:1839`) and the no-override branch (`loader.py:1866`) both apply it, so any importer-defined agent that goes through `resolve()` (or an equivalent) gets the contract "for free."
- ADR-002 C.11 `untrusted_input` ⊥ `exec:*`: enforced via `_validate_untrusted_input_exec`, called both inside `_merge_validated` (override path) and directly in `resolve()`'s no-override branch (`loader.py:1852-1860`) — also role-agnostic.
- Capability tiers (ADR-002 C.10) and the T3 sandbox gate are enforced at `ToolSpec.__post_init__` (`registry.py:81-124`) and at `_deny_reason` (`injector.py:87-95`) — both operate on the resolved `AgentDefinition`/registered `ToolSpec`, not on "is this role predefined or custom," so they are already agent-shape-agnostic.

**ADR-002 sections targeted for amendment — current status, for context:**
- **A.1** (role=class, agent=identity+memory, `docs/platform/agent.md`): ✅ done as a definition. A.2 (per-principal identity) is explicitly ⏳ pending, tied to issue #53 — and is the SAME underlying gap as guard #2 (see above); `main.py`'s AD-5 comment documents the current "role's own permissions become the grant" as a deliberate stopgap decision, not an oversight.
- **D** (role composition, `loader.py:1189+`): documents the current tree, the additive-roles/subtractive-deployments asymmetry, D.16 (rejects multiple inheritance in favor of composition/traits — directly relevant to "extend generic OR a predefined agent," see Approaches), D.17 (inherited contract test suite, `tests/platform_role_contract.py` + `tests/test_role_contract_suite.py`, ✅ done).
- **C.15** (reference backends, ✅ done): ships `InMemoryKnowledgeBase`/`LLMConversationSummarizer`/`LoggingEscalationChannel`/`InMemoryOrderWriter` — orthogonal to this change but shares the "opt-in, fail-closed by default" design philosophy the new Agent API should probably keep.
- **E.18** (live eval pipeline, 🚧 in progress, `src/agents_system/evals/`): scenario-per-role, `live` pytest marker, uses reference backends from C.15. Serving importer-defined agents will eventually need scenario coverage too, but that is downstream of this ADR.
- **F** (stale docs, ✅ done for F.19-21): establishes the precedent this ADR should follow for the `deployment.md` "no generic skills" vs `role.md` "optional skills/" contradiction — fix the doc, record status, don't silently leave it.

## Affected Areas

- `src/agents_system/harness/loader.py:667-668` (`_role_folder`) — hardcoded to `platform_root/roles`; the locator generalization's core change.
- `src/agents_system/harness/loader.py:836-843` (`_extends_target`) — last-segment stripping; must be revisited alongside any locator work, not left silently inconsistent with a richer `extends:` value.
- `src/agents_system/harness/loader.py:880-945` (`_load_role_files`), `:1102-1149` (`_resolve_role_chain`), `:1152-1178` (`load_generic`), `:1809-1882` (`resolve`) — the whole chain assumes "role_type is a name resolvable under platform_root/roles"; widening this is the structural core of the change.
- `src/agents_system/harness/loader.py:1218-1302` (`load_override`) — deployment-override semantics for predefined roles; keep unchanged for backward compatibility.

- `tests/platform_role_contract.py` (`discover_platform_roles`, `EXPECTED_ROLE_TOOLS`) — pins exactly the 8 predefined roles; must stay scoped to `platform_root/roles` only, explicitly excluding importer-defined agents from this platform-only discovery.
- `docs/platform/deployment.md:91-93` vs `docs/platform/role.md:7` — pre-existing skills-location doc contradiction, becomes load-bearing.
- `docs/architecture/adr-002-agent-model-and-capabilities.md` — sections A.1 (`:94`), D (`:1189`), C.15 (`:1112`), E.18 (`:1341`), F (`:1410`) are the ADR-003 amendment targets.
- No `CHANGELOG.md` exists — greenfield for guard #1.

## Approaches

1. **Locator generalization (recommended)** — Replace the implicit "`role_type: str` means a name under `platform_root/roles`" assumption with an explicit, small discriminated locator the loader/factory/main all thread through uniformly: a platform-role name (today's behavior, unchanged), an importer folder path (reads `role.md`/`manifest.md`/`policy.md` from an arbitrary caller-supplied directory the same way `_load_role_files` does today, just parameterized on folder), or an inline `RawDefinition`/spec supplied directly from Python parameters (skips disk entirely). `extends:` resolution is generalized to search the same locator space instead of being silently re-collapsed to a bare name under `platform_root/roles`. `Agent(folder=..., **params)` becomes a thin builder that produces one of these locators (or a fully-built `AgentDefinition` directly) and calls the same `resolve`/`merge`/`build_runtime` primitives already proven for predefined roles.
   - Pros: One resolution/merge/injection code path for every agent shape (predefined, importer-folder, importer-params, importer-extending-predefined) — the library invariants (B.8/B.9 contract, C.10 tiers, C.11 untrusted_input, C.12 command tools) all apply automatically because they already live inside `resolve()`/`merge()`/the injector, agent-shape-agnostic. Minimal duplication.
   - Cons: `_role_folder`, `_extends_target`, `_load_role_files`, `_resolve_role_chain`, `load_generic`, `resolve()` all need signature/behavior changes — a real, if contained, refactor of the loader's core. `_extends_target`'s path-stripping bug must be fixed as part of this, not around it.
   - Effort: Medium-High.

2. **Parallel importer-agent module, bypass the loader for the Python/folder case** — Build a separate `agent_spec.py`/`importer.py` module that independently parses an importer's `role.md`/`manifest.md`/`policy.md` folder (or Python params) into a `RawDefinition`-shaped object, but does NOT reuse `_load_role_files`/`_resolve_role_chain` — it calls `merge()`/`build_runtime()`/the injector directly once it has a `RawDefinition`, and separately resolves an `extends:` target by first trying the new module's own registry, falling back to `load_generic` for predefined-role parents.
   - Pros: Zero changes to `loader.py`'s existing, well-tested predefined-role path — lowest regression risk to the 8 shipped roles and their pinned contract tests.
   - Cons: Two independent implementations of frontmatter parsing / chain-walking / cycle-and-depth checks that must stay behaviorally identical (the loader's own docstrings already treat this class of drift as a real, named risk — e.g. `_extends_target`'s comment about the path form "having to keep meaning what it looks like it means"). Extending a *predefined* role from an importer folder needs careful two-module coordination for the fold direction and validation order.
   - Effort: Medium, but carries ongoing duplication-maintenance cost.

3. **Full loader rewrite around a generic "role source" interface** — Introduce a `RoleSource` protocol (folder-backed, in-memory, or composite) that `RootConfig` composes a list of, and have every current disk-specific function become one concrete implementation of it.
   - Pros: Most extensible long-term (e.g. future non-filesystem sources).
   - Cons: Largest surface change for a feature whose actual driving need (folder + Python-params importer agents, extending either generic or a predefined role) does not require full source pluggability yet — over-engineered relative to the decided scope (Option B, additive inheritance, two guards). Highest review-workload risk given the review-budget guard in this workflow.
   - Effort: High.

## Open design questions — options

**Q1: How does `extends:` reference the packaged generic/predefined agents from an importer folder?**
- (a) Keep `extends: platform/roles/agent` (or a shorter `extends: agent`) working exactly as today for "extend the platform's generic/predefined tree," resolved through the locator's platform-role branch — no importer-side syntax change for this common case.
- (b) Let an importer's `extends:` also reference another importer-defined custom agent by a path relative to the importer's own root (needs the locator work in Approach 1; today this is impossible — `_extends_target` strips it to a bare name and re-resolves under `platform_root/roles`, so it would silently either fail (`DefinitionError`, role not found) or worse, if the bare name happens to collide with a real platform role name, silently extend the WRONG parent).
- Recommendation: (a) unchanged for extending platform/predefined roles; (b) requires the locator generalization and must explicitly reject (not silently collapse) any `extends:` value the resolver cannot place in one of the two allowed locator spaces.

**Q2: The Agent Python API shape.**
- Two entry shapes must produce the SAME `AgentDefinition` shape the loader already produces: `Agent.from_folder(path, **skill_overrides)` (reads `role.md`/`manifest.md`/`policy.md` from `path`, same three-file contract as today) and `Agent(name=..., extends=..., tools=[...], permissions=[...], ..., skills=[...])` (pure Python params, no disk read). Both AND together (folder + params overriding/extending folder content) should be supported per the change intent ("from a folder... AND/OR from Python parameters").
- Recommendation: model both as producing a `RawDefinition` (or a strict superset dataclass) that flows into the EXISTING `_fold_parent_into_child`/`merge`/`resolve` pipeline unchanged — this is what Approach 1 buys.

**Q3: Where do skills live for an importer/custom agent?**
- Today: deployment-only (`deployments/{client}/{role}/skills/`), contradicting `role.md`'s own documented (but unimplemented) "optional skills/ subdirectory."
- Needed: an importer Agent's OWN folder `skills/` subdirectory, and/or skills content supplied as Python parameters, with defined precedence against the existing deployment-override skills mechanism (which should keep working unchanged for predefined roles per the change intent's backward-compatibility requirement).
- Recommendation: extend `_load_skills`'s source resolution (not its `FactoryError`-on-missing-client behavior, which should stay for the deployment-override case) to also check an importer agent's own folder and/or inline-supplied skill content, in a defined order documented in the eventual ADR-003.

**Q4: The runtime-id and registration API for `create_app`.**
- Today: `create_app`'s caller supplies `settings.adapter_runtimes`/`settings.whatsapp_runtime_id` as `{deployment}__{role}` strings, where `role` must already exist under `platform_root/roles`; `main.py`'s lifespan independently re-parses this (duplicate of `openai_adapter.to_model_id`/`parse_model_id`).
- Needed: a way to register an importer-defined `Agent` object directly (not just a role NAME the lifespan re-resolves by string), and a redesigned identity scheme that does not need the `_generic` string sentinel once "generic" is renamed to "predefined" (the sentinel value itself is a literal string baked into two files — a rename must update `main.py:292` and `openai_adapter.py:59,71` together, and ideally collapse them into one shared function to remove the existing duplication).
- Recommendation: (1) consolidate the two independent parsers into one (`openai_adapter`'s versions, imported by `main.py`, deleting the inline duplicate); (2) extend `create_app`/the lifespan to accept pre-built `Agent`/`AgentDefinition` objects directly, not only role-name strings resolved against `platform_root/roles`, while keeping today's string-based path working for predefined roles (backward compatible); (3) settle the sentinel/prefix rename as part of the SAME PR that does the parser consolidation, to avoid a half-renamed state.

**Q5: Backward compatibility for deployment overrides.**
- `load_override`/`merge`/`_validate_tools` (subtractive-only, predefined-role-scoped) should NOT change behavior for existing deployments. Recommendation: leave this path fully intact; the new importer-agent path is additive/parallel, not a replacement.

**Q6: How are the two guards enforced?**
- **Guard 1 (strict SemVer + CHANGELOG on predefined-role tools/permissions changes):** wholly new. Needs: (a) a "last released" reference to diff against — options are a git tag, a published PyPI release marker, or a checked-in "last shipped manifest" snapshot fixture (closest existing precedent: `tests/platform_role_contract.py`'s `EXPECTED_ROLE_TOOLS` literal, which is already a manually-maintained independent expectation — could be extended into a versioned snapshot rather than invented from scratch); (b) a rule that any diff in `tools`/`permissions` for a role under `platform_root/roles` forces a MAJOR bump of that role's `version` field; (c) a CHANGELOG entry requirement, enforced by a new contract-style test (same shape as D.17's tree-walking suite) or a CI step.
- **Guard 2 (explicit `granted_permissions`, nothing inherited without a grant):** the injector ALREADY enforces this correctly (`injector.py:102-169`, `:172-224`, intersection semantics). The actual gap is `main.py`'s lifespan always passing the role's own full permission set as the "grant" (`main.py:357-364`). Recommendation: change the call site so a deployer states permissions explicitly per deployed agent (default empty, never auto-full), which is a wiring change, not new injector logic — and note this is the SAME underlying gap as ADR-002 A.2 (per-principal identity, issue #53); worth resolving both under one design rather than twice.

## Recommendation

Approach 1 (locator generalization) plus the Q1-Q6 answers above. Concretely: widen `resolve()`'s notion of "what a role is" into a small locator (platform-role name | importer folder | inline Python-built definition) that reuses every existing merge/injector/contract-invariant code path unchanged; fix `_extends_target`'s silent path-stripping as part of that widening rather than leaving it inconsistent; consolidate the two independent `{deployment}__{role}` parsers before/while renaming the `_generic` sentinel to whatever "predefined" becomes; keep `load_override`/deployment-override semantics fully untouched for backward compatibility; wire guard #2 as a `create_app`/lifespan call-site change (the injector needs no new logic); treat guard #1 as greenfield tooling, likely extending `tests/platform_role_contract.py`'s existing "independent literal expectation" pattern into a versioned snapshot. Keep `tests/platform_role_contract.py`'s discovery scoped strictly to `platform_root/roles` so importer-defined agents never leak into the predefined-role pin.

## Risks

- `_extends_target`'s last-segment stripping (`loader.py:843`) is a real, already-flagged footgun: any locator work that does not explicitly fix it will let a mistyped or importer-referencing `extends:` silently resolve to the WRONG same-named platform role instead of failing loudly.
- Renaming `_generic` → predefined touches two independently-maintained parsers (`main.py:292`, `openai_adapter.py:59,71`); a partial rename leaves them silently inconsistent — the same drift class ADR-002 F.19-21 already document elsewhere in this repo for stale docs.
- `tests/platform_role_contract.py`'s `EXPECTED_ROLE_TOOLS` is a hand-maintained literal; if the locator generalization changes how `discover_platform_roles()`/`platform_roles_dir()` walks disk, this pin could silently start including importer content unless explicitly scoped — must stay `platform_root/roles`-only by contract, not by accident.
- Guard #1 has no existing tooling to build on beyond the free-text `version` string and the `EXPECTED_ROLE_TOOLS`-style manual pin pattern — real design/build effort, and "what counts as the last released version" (git tag vs. snapshot fixture vs. PyPI) needs an explicit decision before implementation, likely in sdd-design.
- Guard #2 overlaps ADR-002 A.2 (per-principal identity, ⏳ pending, issue #53) — implementing it in isolation risks re-solving the same "who actually grants what" problem twice under two names; recommend the eventual design/tasks phase explicitly cross-reference A.2 rather than treat guard #2 as unrelated new work.
- The `docs/platform/deployment.md` vs `docs/platform/role.md` skills-location contradiction must be resolved as part of this change (not deferred), since the new Agent-folder skills story makes the currently-false "no generic skills" claim actively misleading rather than a harmless doc nit.
- ADR-002's A.1/D/C.15/E.18/F sections are dense Decision/Rationale/Alternatives/Status records with their own internal cross-references and a documented PR-slicing convention (see the C section's slicing note) — ADR-003 should add pointers/amendments to each, not rewrite them in place, to avoid orphaning existing rationale (mirroring how F.19-21 handled superseding earlier stale-doc findings within the same ADR).
- `platform_role_contract.py`'s own docstring explains its `EXPECTED_ROLE_TOOLS` literal exists specifically so "a manifest edit has to be a deliberate, reviewed change to this file too" — any guard-#1 snapshot mechanism should follow the same "deliberate, reviewed, independent expectation" philosophy rather than auto-deriving from whatever is currently on disk (which would defeat the point of a version-bump gate).

## Ready for Proposal

Yes. The two guards, the additive-inheritance decision (Option B — extend generic OR a predefined agent), and the library invariants that must hold universally are already decided by the change intent. The concrete locator shape (platform-role name | importer folder | inline Python definition), the exact `Agent` Python API surface, the skills precedence order, and the SemVer/CHANGELOG mechanism's "what counts as released" question are the open items sdd-propose/sdd-design should settle next — all are scoped and traceable to specific existing code (see Affected Areas), none require further exploration before proposing.

## Key Learnings

1. `_extends_target` in `harness/loader.py:836-843` silently strips `extends:` to its last path segment, so path-form values are cosmetic today, not functional — any locator generalization must fix this rather than build around it.
2. The generic agent already exists as `platform/roles/base` (abstract) → `platform/roles/agent`; the 8 packaged roles already extend it — renaming to "predefined" is a terminology change over an already-correct tree, not a structural rebuild.
3. The permission injector (`harness/injector.py`) already enforces real explicit-grant intersection semantics; guard #2's actual gap is that `main.py`'s lifespan always passes a role's full resolved permission set as the "grant" rather than a deployer-curated subset — a call-site wiring fix, not new injector logic.
4. Runtime-id parsing (`{deployment}__{role}`, `_generic` sentinel) is independently duplicated in `main.py` and `integration/openai_adapter.py`, a drift risk that should be consolidated as part of any rename.
5. No SemVer/CHANGELOG tooling exists anywhere in the repo today — guard #1 (strict SemVer + CHANGELOG on predefined-role tool/permission changes) is greenfield work, not a refactor of existing machinery.
